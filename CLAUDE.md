# Furni — SaaS 3D-конфигурации мебели

Инструкции проекта. Читаются в каждой сессии. Полное ТЗ — `docs/SPEC.md`.

## Что строим

Мультитенантный SaaS: мебельный магазин встраивает на свой сайт конфигуратор товара и планировщик помещения. Покупатель собирает сцену — магазин получает заявку со спецификацией.

## Главное правило проекта

**Производительность — это функциональное требование, а не оптимизация «потом».**

Целевое устройство — Redmi Note 12 / iPhone 12 / iPad 9. На нём сцена из 20 объектов обязана держать **60 fps p50 и ≥45 fps p95**. Любой PR, который выводит показатели за бюджет (`packages/shared/src/budgets`), не проходит CI и не мержится. Если фича не помещается в бюджет — меняется фича, а не бюджет.

## Архитектурные правила, которые нельзя нарушать

### 1. Объекты Three.js никогда не попадают в реактивность Vue

Vue оборачивает вложенные объекты в `Proxy`. Если `Object3D`, `BufferGeometry`, `Material`, `Texture` или `WebGLRenderer` попадёт в `reactive()`, `ref()` или в state Pinia — каждое обращение к `.position.x` внутри цикла рендера пойдёт через перехватчик. Это стоит порядка производительности и находится не сразу.

```ts
// ЗАПРЕЩЕНО
const mesh = ref(new Mesh(geo, mat))
const store = reactive({ scene: new Scene() })

// ПРАВИЛЬНО
const mesh = shallowRef(markRaw(new Mesh(geo, mat)))
const viewer = markRaw(new Viewer(canvas))
```

Правило проверяется линтом (`eslint-local-rules/no-reactive-three`). Не отключать.

### 2. Горячий путь — императивный Three.js, не компоненты

Перетаскивание, снаппинг, коллизии, переключение LOD, цикл рендера живут в `packages/viewer` и не знают о Vue вообще. Этот пакет собирается и тестируется отдельно, без фреймворка.

Vue отвечает только за UI-хром: панели, каталог, формы, роутинг. TresJS — тонкий слой монтирования, изолирован в `apps/web/src/components/SceneCanvas.vue`. Если TresJS начнёт мешать — заменяется на ручное монтирование без переписывания логики сцены.

### 3. Ноль обновлений Vue-компонентов на кадр

Состояние сцены синхронизируется в UI через throttle (не чаще 10 Гц) и только теми полями, которые реально отображаются. Позиция объекта во время перетаскивания в Pinia **не пишется** — только по окончании жеста.

### 4. Цена считается на сервере

Клиент считает предварительную цену для мгновенного отклика UI. Итоговая цена в заявке — всегда пересчёт на сервере по правилам тенанта. Клиентскому расчёту не доверяем никогда.

### 5. Мультитенантность через RLS

Каждый запрос выполняется в транзакции с `SET LOCAL app.tenant_id`. Политики RLS в БД — это страховка от ошибки в коде приложения, а не основной механизм. Фильтр по `tenantId` в коде тоже обязателен. Новая таблица без RLS-политики — баг.

### 6. Геометрия не хранится в сцене

`scenes.doc` — это JSON со ссылками на SKU и трансформациями. Никаких вершин, мешей и материалов в документе сцены. Схема — `packages/shared/src/scene`, версионируется, миграции документов обязательны при смене версии.

## Структура

```
apps/api          NestJS + Prisma + PostgreSQL. REST + WebSocket
apps/web          Vue 3 + Vite. Планировщик, конфигуратор, кабинет
packages/shared   Zod-схемы, типы, бюджеты. Общие для api и web
packages/viewer   3D-ядро на чистом Three.js. Без Vue
packages/embed    Web Component <furni-configurator> для сайтов магазинов
tools/pipeline    Обработка ассетов: Blender + gltf-transform
tests/perf        Перф-гейт на Playwright
```

Зависимости идут только внутрь: `web` → `viewer`, `shared`. `viewer` не зависит ни от чего, кроме `three` и `shared`. Обратные зависимости запрещены.

## Стек

Vue 3.5 Composition API `<script setup>` · TypeScript strict · Vite · Pinia · Reka UI · Tailwind · TresJS (тонкий слой) · Three.js · NestJS · Prisma · PostgreSQL 16 · Redis + BullMQ · S3

## Конвенции кода

- TypeScript strict, `any` запрещён. Для внешних данных — Zod-парсинг на границе.
- Vue: только `<script setup lang="ts">`, Composition API, никакого Options API.
- Логика Three.js — в классах и composables, не в компонентах.
- Именование: `PascalCase` компоненты, `camelCase` composables с префиксом `use`, `SCREAMING_SNAKE` константы бюджетов.
- Единицы измерения в системе — **миллиметры целыми числами** во всех данных, конвертация в метры только на входе в Three.js. Плавающая точка в размерах мебели порождает ошибки стыковки.
- Ось Y — вверх. Origin модели — низ-центр габарита.

## Тестирование

- `packages/viewer` — unit-тесты на снаппинг, коллизии, математику (Vitest, без DOM).
- `packages/shared` — тесты схем и правил.
- `apps/api` — интеграционные тесты на реальной БД в Docker, обязательно с проверкой изоляции тенантов.
- `tests/perf` — Playwright сценарий: собрать сцену из 20 объектов, снять fps и draw calls, сравнить с бюджетом. Запускается в CI на каждый PR.

Перед коммитом: `pnpm lint && pnpm typecheck && pnpm test`.

## Чего не делать

- Не добавлять real-time shadow maps в интерактивном режиме — только в refined.
- Не грузить движок до взаимодействия пользователя в embed-виджете.
- Не тянуть тяжёлые зависимости в `packages/embed` — бюджет 8 КБ gzip.
- Не создавать таблицы без `tenant_id` и RLS.
- Не использовать `JSON.parse(JSON.stringify())` на объектах сцены.
- Не писать в Pinia на каждый кадр анимации или перетаскивания.

## Текущий статус

Каркас. Реализовано: схема БД с RLS, схемы документа сцены и DSL правил, ядро вьюера с адаптивным качеством и телеметрией, скелет API, перф-гейт.

Не реализовано (в порядке приоритета — см. `docs/BACKLOG.md`):
1. Пайплайн ассетов — Blender-скрипты и gltf-transform написаны как заготовки, нужен прогон на реальных моделях.
2. Планировщик: рисование стен, снаппинг доведён только до примагничивания к сетке.
3. Параметрическая сборка — есть типы DSL, нет исполнителя геометрии.
4. Кабинет тенанта.
5. Биллинг.
